# Dart Syntax Patterns

Pure language syntax reference for Dart code generation. These patterns apply to any domain.

---

## File Layout

A Dart package follows the pub layout convention:

```
lib/<package>.dart            # Public entry point (exports)
lib/src/<module>.dart         # Implementation modules (one per spec module)
test/<module>_test.dart       # Tests
pubspec.yaml                  # Package manifest
analysis_options.yaml         # Lints (usually `include: package:lints/recommended.yaml`
                              #   or `package:flutter_lints/flutter.yaml`)
```

- Everything under `lib/src/` is package-private by convention; the public API
  surface is whatever `lib/<package>.dart` re-exports:

```dart
// lib/my_package.dart
export 'src/rate_limiter.dart' show RateLimiter;
```

- A Flutter app additionally has platform directories (`android/`, `ios/`,
  `web/`, …) created by `flutter create`. Those are **externally owned
  scaffolding** — never spec modules, never regenerated by spec tooling.

---

## Source-to-spec mapping

- **`lib/src/<snake_case>.dart`** → one spec module. File stem is snake_case;
  the spec `name` is PascalCase (e.g. `rate_limiter.dart` → `RateLimiter.toml`).
  The spec's `paths.source` points at `lib/src`.
- **`lib/<package>.dart`** (the export barrel) → not a spec module; it exposes
  the public surface of the modules.
- **`main.dart` / `lib/main.dart`** (Flutter app entry) → not a spec module; it
  wires modules together.
- **Generated glue** (`*.g.dart`, `*.freezed.dart`, `frb_generated.dart`, …) →
  externally owned; never a spec module.

---

## Naming Conventions

- Types (classes, mixins, enums, extensions, extension types, typedefs):
  `UpperCamelCase`
- Members, functions, variables, parameters: `lowerCamelCase`
- Files and directories: `lowercase_with_underscores`
- Constants: `lowerCamelCase` (not SCREAMING_CAPS — per Effective Dart)
- Private (library-scoped) symbols: leading underscore (`_helper`)

## Doc Comments

Use `///` for public API documentation; the first sentence is the summary.

```dart
/// A token-bucket rate limiter.
///
/// Refills [capacity] tokens per [interval]. Thread-safe within one isolate.
class RateLimiter {
  /// Attempts to consume [tokens], returning `false` when exhausted.
  bool tryConsume(int tokens) { ... }
}
```

Square-bracket references (`[capacity]`) link to in-scope identifiers.

## Null Safety

All generated code is sound-null-safe:

- Non-nullable by default; `T?` only where absence is a real state.
- `late` only for genuinely deferred initialization with a documented invariant.
- No `!` (null assertion) in generated code — restructure so the type system
  carries the proof, or handle the null case explicitly.

## Error Handling

- Programming errors (violated preconditions): `ArgumentError`, `StateError` —
  thrown, not caught.
- Recoverable domain failures: a dedicated exception type per module:

```dart
/// Thrown when the device rejects a command.
class DeviceRejectedException implements Exception {
  DeviceRejectedException(this.reason);
  final String reason;
  @override
  String toString() => 'DeviceRejectedException: $reason';
}
```

- Alternatively, model expected failure as data with a sealed result type:

```dart
sealed class ParseResult {}
class ParseOk extends ParseResult { ParseOk(this.value); final Frame value; }
class ParseErr extends ParseResult { ParseErr(this.message); final String message; }
```

Pick one style per module and state it in the module spec's prose.

## Async

- `Future<T>` for one-shot async operations; `Stream<T>` for sequences
  (events, notifications, sensor feeds).
- `async`/`await` bodies; never raw `.then()` chains in generated code.
- Cancellation: `StreamSubscription.cancel()`; long-lived objects that own
  subscriptions expose `Future<void> dispose()` and document it.

## Class Patterns

### Immutable value type

```dart
class Reading {
  const Reading({required this.celsius, required this.timestamp});
  final double celsius;
  final DateTime timestamp;
}
```

### Service with lifecycle

```dart
class SensorService {
  SensorService(this._transport);
  final Transport _transport;
  StreamSubscription<List<int>>? _sub;

  Future<void> start() async { ... }
  Future<void> dispose() async { await _sub?.cancel(); }
}
```

### Interface + implementation

Dart classes are implicit interfaces; depend on an abstract class and inject
the concrete one:

```dart
abstract class Clock {
  DateTime now();
}
class SystemClock implements Clock {
  @override
  DateTime now() => DateTime.now();
}
```

## Test File Pattern

`test/<module>_test.dart` using `package:test` (or `package:flutter_test` in a
Flutter package):

```dart
import 'package:test/test.dart';
import 'package:my_package/my_package.dart';

void main() {
  group('RateLimiter', () {
    test('consumes up to capacity', () {
      final limiter = RateLimiter(capacity: 2);
      expect(limiter.tryConsume(2), isTrue);
      expect(limiter.tryConsume(1), isFalse);
    });
  });
}
```

- One `group` per type under test; `test` names are behavior sentences.
- Widget tests use `testWidgets` + `WidgetTester` and live in the same layout.
