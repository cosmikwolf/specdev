# egui-Rust Reverse Flow — Source → Spec Audit

The audit pipeline compares generated Rust source against the spec to
detect drift. This file documents which tree-sitter queries and
recognition patterns the egui-rust codegen relies on.

## Adapter Reuse

This domain reuses `specdev/languages/rust/` unchanged. The default Rust
adapter covers:

- Struct / enum declarations
- `impl` block discovery (both inherent and trait impls)
- Function signature extraction (name, params, return type)
- Attribute parsing (`#[derive(...)]`, `#[cfg(...)]`, `#[test]`)

Audit queries live in `specdev/languages/rust/audit.scm`. No egui-
specific tree-sitter additions are required for v1 — the patterns
below describe how the existing queries are interpreted for egui spec
drift detection.

## Drift Categories

### Widget drift

Generated view function body contains `ui.*` calls; the spec declares
a `widgets[]` list.

- Each spec widget has an expected call signature (see
  `gen-view.md` widget kind table). The audit walks the view function
  body and matches calls to widget entries by call signature +
  binding/label text. A missing expected call or an extra unexpected
  call is a drift finding.
- Widget order matters for spec fidelity but not for runtime
  correctness. Report mismatched order as `info`, not `warning`.

### Action drift

Spec `actions[]` should appear as methods on the view struct's `impl`
block (or as free functions in the view module when the action is
stateless).

- Missing method for a declared action → `error`-severity drift.
- Extra method not in the spec → `warning` (could be a private helper;
  do not assume the spec is wrong).
- Parameter-count mismatch → `warning` with a hint to check
  `actions[].params[]`.

### Store field drift

Declared store fields should match the generated struct's fields.

- Field in spec but not in struct → `error`.
- Field in struct but not in spec → `warning` (may be a cached
  internal, but spec should declare it).
- Type mismatch between spec `type` (after `type_map.rust` resolution)
  and the struct field type → `warning`.

### Panel mount drift

`architecture.toml` mounts should match the `impl eframe::App::update`
body's panel constructors.

- Recognize `egui::TopBottomPanel::top`, `::bottom`,
  `egui::SidePanel::left`, `::right`, `egui::CentralPanel::default` call
  patterns via tree-sitter's `call_expression` matcher.
- Map each found call to a slot (`top` / `bottom` / `left` / `right` /
  `central`). A slot mismatch between spec and source is an
  `error`-severity drift.
- When `navigation` is declared, the central panel should contain a
  `match self.current_screen` dispatch — audit checks for that and
  flags missing dispatch as `warning`.

### Persistence drift

Stores with `persisted = true` should have corresponding calls in the
`save()` impl and a `load`-on-init pattern in `AppState::new`.

- Missing `save()` call for a persisted store → `error`.
- `save()` call for a store not declared `persisted` → `warning`.

## Recognition Patterns

### Detecting `impl eframe::App`

```scm
(impl_item
  trait: (scoped_type_identifier
    path: (identifier) @crate (#eq? @crate "eframe")
    name: (type_identifier) @trait (#eq? @trait "App"))
  type: (type_identifier) @app-struct)
```

Extract the `@app-struct` name as the `AppState`-equivalent struct. Its
`update` method body contains the panel routing to audit.

### Detecting view `show` methods

View structs are identified by matching the spec's view names. For each
declared view, search for:

```scm
(impl_item
  type: (type_identifier) @struct (#eq? @struct "<ViewName>")
  body: (declaration_list
    (function_item
      name: (identifier) @fn (#eq? @fn "show"))))
```

Then walk the function body's `call_expression` nodes, filtering for
receiver `ui` (or `ctx` for root views) to extract widget calls.

### Detecting store structs

```scm
(struct_item
  name: (type_identifier) @name (#eq? @name "<StoreName>")
  body: (field_declaration_list) @fields)
```

Walk `@fields` for `field_declaration` nodes to extract `(name, type)`
pairs; compare against spec `fields[]`.

## Generated-file Markers

Generated files include a header comment:

```rust
// <spec-authoritative marker>
// Generated by specdev-codegen from <path/to/spec>.
// DO NOT EDIT — update the spec and regenerate.
```

The audit pipeline keys on this marker to decide whether a file is in
scope for drift detection. Files without the marker are hand-authored
and audited by a separate rule (`unmanaged_file` — warning in the
`/spec-audit` skill, not in this domain).

---

## Drift Resolution

When drift is found, the resolution hierarchy is:

1. **Spec is authoritative** — regenerate the code from the spec. This
   is the default fix.
2. **Code intent was correct** — update the spec to match and
   regenerate (no-op regeneration confirms the round-trip).
3. **Intentional divergence** — accept the drift by adding a
   `# drift: accepted` marker line to the spec entry. Future audit runs
   skip the accepted drift but still report it as `info`.

Generated code is never edited directly to resolve drift — the
authoritative source is always the spec.
